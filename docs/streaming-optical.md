# 大容量の光学転送

64 MiB・2,000ファイルという転送制限を撤廃した。8 MiBを超える選択、
一覧の見積りが512 KiBを超える選択、または2,000ファイルを超える選択は、
QR / FX2とも自動的にストリーミング形式を使う。これは形式の切替条件で、
超えた選択を拒否する条件ではない。画面と操作方法は変わらない。

小さな選択は、下記の実測で速さを維持できたDCF2/DCB1・圧縮・Fountain経路を使用する。
旧形式の受信パーサに残るサイズ検査は、旧形式をメモリに展開するときの保護であり、
新形式の転送には適用されない。新形式を送受信する両端には更新版が必要。

## データとメモリ

- 送信準備では、ファイルをストリームでSHA-256検算する。内容を束ねた巨大な配列や
  一時コピーは作らず、表示時に元ファイルから64 KiB単位で読む。送信中のサイズ・更新日時の
  変化を拒否し、受信側でも各ファイルのSHA-256を検証する。
- 受信は最大4区画のFountain状態だけをメモリに保持する。復元済み区画と、退避する
  未完区画の既知ブロックをディスクに書く。既知ブロック・完了フラグもディスクに置くので、
  転送量に比例するビットマップや重複履歴をメモリに作らない。未完区画は後の周回で補完する。
- 全区画が揃ったらディスク上の束を順に読み、ファイルへ書きながらSHA-256を検証する。
  全ファイルの検証後にディレクトリをrenameして公開する。失敗・停止・リセット・期限切れ・
  通常終了では、その受信が所有する一時データを削除する。最終保存中は最大で転送量の約2倍の
  空きディスクが必要。アプリ再起動をまたぐ受信再開は実装していない。
- ファイル内容のメモリ量は総バイト数に依存しない。従来からのファイル一覧と送信メタデータは
  ファイル数に応じたメモリを使う。新形式の内容は圧縮しない。

総サイズ・区画番号・復元ブロック数・ファイル数は64ビット。表示要求の連番も64ビットにした。
ネイティブの長さ表現は符号付き64ビット、ブラウザで正確に扱う範囲は2^53−1バイト
（約8 PiB）。いずれも一週間で送れる120～240 GBを十分に超える。
フレーム要求のJavaScript連番も2^53−1まで正確で、旧32ビットの周回制限はない。
OSのファイルサイズ・空きディスク・ファイル一覧の実装上の制約は引き続きある。

## 光学フレーム D1/0D

整数はlittle endian。ヘッダ48バイトの後に固定長のブロックが続く。
QRは最大2,953バイト、FX2は選択した誤り訂正の既存パッチ寸法を使う。

| Offset | Bytes | 内容 |
|---:|---:|---|
| 0 | 2 | `D1 0D` |
| 2 | 2 | 転送ID先頭16ビット（Fountain seed） |
| 4 | 4 | 区画内フレーム番号 |
| 8 | 8 | 区画番号、0から |
| 16 | 8 | 束の総バイト数 |
| 24 | 16 | 転送ID（GUIDのバイト表現） |
| 40 | 4 | 区画全体のFNV-1a |
| 44 | 2 | ブロック長 |
| 46 | 2 | 予約、0 |

区画は65,536バイト（末尾のみ短い）。フル区画のブロック数をBとして、表示要求2B枚を
1区画に割り当てる。最初の区画ブロック数分は無加工のsystematicブロック、残りは従来の
Fountain演算による修復用ブロック。最後の区画まで行くと先頭に戻り、次の周回では異なる
修復ブロックを送る。区画内番号が区画ブロック数未満ならsystematic、それ以降なら
その数を引いた値が従来Fountainのsequenceとなる。

ディスクへの退避では未解決の方程式を捨て、解決済みブロックを保存する。
同じ区画に長時間留まっても未解決方程式の数を制限し、既知ブロックを維持してdecoderを作り直す。
転送途中から読み始めたり、一部の画面を落とした場合も後の周回で不足分を集められる。
100%の修復枠を用意するため、無損失時にも表示では冗長データが流れる。

束FXB3は `FXB3`、ラベル（BinaryWriterのUTF-8文字列）、ファイル数（i64）、
続いて各ファイルの相対パス（同じ文字列形式）、サイズ（i64）、SHA-256（32バイト）、
内容の繰り返し。一覧全体をJSONとして一括展開しない。

HTTPのpacked QR応答FQR1ヘッダは既存の12バイトのまま。連番欄は要求連番の下位32ビットの
照合に使い、JavaScript側は要求時の完全な連番を保持する。光学フレームの区画番号は64ビット。

## 再現試験

実カメラ・画面表示・音を使わない。大容量ファイルは指定のWORK以下だけに作り、試験完了時に削除する。
LinuxではMemAvailableを250 msごとに確認し、9 GiB未満で試験プロセスを停止する。
メモリは送信・符号化・復号・受信・検算を同居させたプロセスのRSSを測定する。

```sh
dotnet run --project tests/Xfer.Streaming.csproj -c Release --artifacts-path BUILD -- WORK selftest
dotnet run --project tests/Xfer.Streaming.csproj -c Release --artifacts-path BUILD -- WORK fx2 2147549185
dotnet run --project tests/Xfer.Streaming.csproj -c Release --artifacts-path BUILD -- WORK picture 73400320
dotnet run --project tests/Xfer.SmallBenchmark.csproj -c Release --artifacts-path BUILD -- WORK
```

`selftest` は2,001ファイル、ディスク退避・再送、重複・逆順・損失、8 TiBのメタデータ、
32ビット超の番号・ブロック数、QRラスタ復号、破損・不正パス拒否と後片付けを検証する。
`fx2` は全データを製品のFX2画面セル符号器と復号器に通す。大容量では4 CPU workerで符号器を
実行し、理想的な無損失経路で不要な修復枠だけを省略する。画像のマーカー検出はこの試験に含まない。
`picture` は製品のFx2Pictureから1920×1020画素を生成し、Fx2Readerのマーカー検出・
セル読取り・復号から受信保存までを、修復枠も含む通常の表示順序で通す。
いずれも元ファイルとのSHA-256一致を必須にする。

`SmallBenchmark` は5.7 MiBの乱数ファイルを旧形式のまま画面セル符号化・受信保存まで3回流す。
`-p:ProductSource=BASELINE` で旧ソースにも同じ試験を適用できる。

### 小容量の経路を残す理由

旧版との互換性を必要条件とはしていない。同じ5,976,883 bytes（5.7 MiB）の乱数ファイルで、
全表示パッチ（修復枠を含む）のFX2セル符号化・復号・保存を3回ずつ測定した。

- 変更前 `60751c6`：中央値4.1419秒、28,275パッチ。
- 変更後の通常経路：中央値3.9839秒、28,316パッチ。バイト一致、従来の速度を維持。
- 別の連続比較で、変更後の通常経路：中央値3.4381秒、28,148パッチ。
- 同じ連続比較で、新ストリーミング形式を小容量にも強制：中央値4.4980秒、60,673パッチ。

新形式に統一するとこの試料では処理時間が約31%増え、表示に必要なパッチが約2.16倍になる。
この実測差を理由に、小容量の高速経路を残した。新形式は区画ごとの修復枠で長時間の
大容量転送を処理する。小容量に新形式を強制する比較は次で再現できる。

```sh
dotnet run --project tests/Xfer.Streaming.csproj -c Release --artifacts-path BUILD -- WORK small-stream
```

既存C#回帰11件、JavaScript21件（既存20件＋新形式検査）、FX2 selftest、
HeadlessのQR/FX2合成カメラ往復、Chromium/WASMブラウザ回帰、実HTTP smoke、
Diagnostics、FocusHold、ShutdownがPASS。HTTP smokeには2,001ファイル・64 KiB超の
選択JSONを追加し、HTTPの一般リクエスト長が別のファイル数制限にならないことも確認した。
ファイル選択リクエストの許容量は実際に選べる一覧のJSON最大長から求め、一覧全体を送れる。
本体とLinuxデスクトップ版のビルドも成功。実カメラ、Windows実行、UI実画面操作は行っていない。

完了時に試験用WORK（入力・復元結果・一時受信データ・隔離ビルド出力）を削除し、
